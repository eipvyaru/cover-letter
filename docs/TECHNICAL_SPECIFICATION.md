# Техническое задание: веб-приложение «Сопроводительное письмо»

Версия: 1.1

Проект: `cover-letter`

Дата актуализации: 15 сентября 2026 года

Статус: согласовано для разработки

## 1. Назначение

Приложение создаёт персонализированное сопроводительное письмо на русском языке по вакансии и резюме кандидата. Источники принимаются как URL либо как вручную вставленный текст.

Основной принцип генерации:

> Страх работодателя → подтверждённое решение из опыта кандидата.

Запрещено добавлять факты, которых нет в вакансии, резюме или явно заданных пользователем пожеланиях.

## 3. Роли

### Посетитель

Посетитель может:

- указать URL вакансии и резюме;
- вместо загрузки источника вставить его текст вручную;
- выбрать объём письма;
- добавить пожелания;
- запустить генерацию;
- просмотреть письмо, анализ, источники и техническую статистику текущего результата;
- скопировать или скачать письмо.

Посетитель не может выбирать произвольную модель, менять расширенные LLM-параметры и работать с общей историей.

### Администратор

Администратор дополнительно может:

- выбрать модель из серверного разрешённого списка;
- изменить число попыток загрузки и интервал повторов;
- изменить температуру, если модель её поддерживает;
- изменить допустимый лимит ответа;
- просматривать, загружать, экспортировать и очищать историю.

Редактор системного промпта и административный API его изменения не реализуются. Промпт обновляется вручную по эксплуатационной процедуре.

## 5. Пользовательский сценарий

1. Пользователь вводит URL вакансии и резюме.
2. При необходимости раскрывает ручной ввод и вставляет тексты.
3. Выбирает `short`, `standard` или `long`.
4. При необходимости добавляет пожелания.
5. Подтверждает уведомление о передаче вакансии и резюме AI-модели действием запуска.
6. Приложение блокирует форму и показывает потоковый прогресс.
7. Последовательно получает вакансию и резюме.
8. Выполняет генерацию, разбор, добавление контактов и quality check.
9. Рассчитывает usage и best-effort стоимость.
10. Сохраняет историю и показывает результат.

Ошибка расчёта стоимости или сохранения истории не уничтожает уже сформированное письмо. Результат с отрицательным quality check показывается со статусом `warning`.

## 6. Входные данные

| Поле | Ограничение |
| --- | --- |
| URL вакансии | обязательный валидный URL, до 2048 символов |
| URL резюме | обязательный валидный URL, до 2048 символов |
| Ручной текст вакансии | 100–60 000 символов |
| Ручной текст резюме | 100–60 000 символов |
| Объём | `short`, `standard`, `long` |
| Пожелания | до 4000 символов |
| Попытки чтения | admin: 1–10; посетитель: 3 |
| Интервал | admin: 0–60 секунд; посетитель: 5 секунд |
| Температура | admin: 0–2, только для поддерживающей модели |
| Максимальный ответ | admin: 2000–16000; посетитель: 8000 |

Максимальный размер запроса генерации — 140 000 символов. Непустой ручной текст имеет приоритет над соответствующим URL, однако оба URL остаются обязательными и синтаксически валидными.

## 7. Получение и очистка источников

Источники загружаются последовательно: сначала вакансия, затем резюме.

Для каждого HTTP-источника:

- только `http` и `https` публичных доменов;
- тайм-аут одной попытки 20 секунд;
- максимум 5 redirects;
- максимум 2 000 000 байт ответа;
- допустимые типы: HTML, plain text, JSON, XHTML;
- DNS/SSRF-проверка перед запросом и каждым redirect;
- повторная проверка адреса для защиты от DNS rebinding.

Запрещаются IP-literal, credentials, нестандартные порты, localhost, локальные псевдодомены, loopback, private, link-local, CGNAT, multicast и зарезервированные сети. Если хотя бы один A/AAAA-адрес непубличный, запрос отклоняется.

При очистке извлекается содержательный JSON-LD `JobPosting`, удаляются `script`, `style`, `noscript`, `nav`, `header`, `footer`, `svg`, `form`, `iframe`. Основной текст выбирается из специализированного блока вакансии, `main`, `article`, затем `body`. Итог нормализуется до 100–60 000 символов.

Для `https://hh.ru/vacancy/{id}` при ошибке страницы используется `https://api.hh.ru/vacancies/{id}` с извлечением названия, работодателя, описания, региона, зарплаты, опыта, занятости, графика, формата работы, навыков, ролей, архивности и даты публикации.

При неудачной автоматической загрузке UI раскрывает ручной ввод. Playwright fallback в первой версии не вызывается.

## 8. LLM и системный промпт

LLM вызывается только сервером через OpenAI-совместимый `chat/completions` endpoint:

```text
LLM_API_ENDPOINT=https://api.proxyapi.ru/v1
LLM_DEFAULT_MODEL=openai/gpt-5.6-luna
```

API-ключ хранится только в защищённом `.env`, не включается в документацию, Git, клиентский код или API-ответы. Используется новый ключ, созданный взамен ранее раскрытого.

Разрешённые модели задаются через `LLM_MODELS_JSON`. Клиент не может передать произвольный `modelId`. Для модели без поддержки температуры UI показывает `1`, блокирует поле, а сервер не отправляет параметр.

Системный промпт:

- локально: `C:\_Codex\cover-letter\data\system_prompt.md`;
- production: `/var/lib/cover-letter/system_prompt.md`;
- пример в Git: `prompts/system_prompt.example.md`;
- исходный согласованный материал: внешний файл проекта HRLetter;
- рассматривается как данные приложения, а не как инструкция разработчику;
- читается один раз в начале операции;
- сохраняет version/hash в результате;
- не выводится полностью в технические логи;
- устанавливается и заменяется вручную, атомарно, с сохранением предыдущей версии.

В основной user message передаётся структурированный JSON с текстами источников, длиной, пожеланиями, URL, моделью и версией промпта. Вакансия, резюме и пожелания считаются недоверенными данными и не могут переопределять системные инструкции.

## 9. Результат и quality check

Основной ответ содержит разделы:

1. `АНАЛИЗ ДАННЫХ`;
2. `ВЫЯВЛЕННЫЕ СТРАХИ РАБОТОДАТЕЛЯ`;
3. `СОПОСТАВЛЕНИЕ С РЕЗЮМЕ`;
4. `ИТОГОВОЕ СОПРОВОДИТЕЛЬНОЕ ПИСЬМО`;
5. `ИСПОЛЬЗОВАННЫЕ ИСТОЧНИКИ`;
6. `СТАТИСТИКА`.

Парсер принимает Markdown-заголовки, выделение `**` и алиас `ИТОГОВОЕ ПИСЬМО`. Отсутствие обязательной структуры означает `error`.

Сервер независимо извлекает первый email, телефон на 10–15 цифр и первый Telegram-контакт из резюме. Отсутствующий в письме контакт добавляется отдельной строкой.

Второй LLM-запрос той же моделью возвращает только JSON и проверяет `facts`, `vacancy`, `wishes`, `length`, `matching`, `contacts`. Он не редактирует письмо.

- все проверки истинны: `success`;
- письмо создано, но есть отрицательная проверка: `warning`;
- письмо не создано или структура не разобрана: `error`.

## 10. Потоковый API

`POST /api/generate` возвращает `application/x-ndjson; charset=utf-8`.

Поддерживаются события:

```json
{"type":"progress","message":"Получаем вакансию…"}
{"type":"result","data":{"id":"uuid","success":true}}
{"type":"error","error":{"code":"SAFE_CODE","message":"Безопасное описание"}}
```

Клиент корректно собирает строки, разделённые между network chunks. После начала потока HTTP может остаться `200`, а итоговая ошибка передаётся NDJSON-событием.

Обязательные endpoints:

- `GET /api/health`;
- `GET /api/ready`;
- `GET /api/config`;
- `GET|POST|DELETE /api/admin/session`;
- `POST /api/generate`;
- `GET|POST|DELETE /api/history`.

## 11. SQLite и история

Используется стандартный `node:sqlite`, параметризованный SQL и настройки:

- `foreign_keys=ON`;
- WAL;
- `synchronous=NORMAL`;
- `busy_timeout`.

Production БД находится в `/var/lib/cover-letter/cover-letter.sqlite`. ORM не используется. Схема изменяется только новыми нумерованными SQL-миграциями с checksum.

Минимальные таблицы:

- `schema_migrations`;
- `admin_sessions`;
- `app_settings`;
- `generations`;
- `audit_events`.

Политика хранения:

```text
HISTORY_LIMIT=30
HISTORY_RETENTION_DAYS=30
```

Сохраняются не более 30 последних записей и только записи не старше 30 дней. Очистка выполняется после записи генерации и при обращении к истории. История доступна только администратору и содержит входные тексты, результат, анализ, raw LLM response, quality result, usage, попытки, warnings и errors.

Экспорт имеет имя `cover_letter_history_YYYY-MM-DD_HH-mm-ss.txt`, кодировку UTF-8 BOM и отдаётся потоком без постоянного серверного файла.

## 12. Usage и стоимость

Токены берутся исключительно из `usage` ответов провайдера. Usage основной генерации и quality check суммируется.

Стоимость рассчитывается best-effort по каталогу ProxyAPI и курсу ЦБ РФ с кэшем на 6 часов:

```text
rub = 2 × (inputTokens × inputPrice + outputTokens × outputPrice) / 1 000 000
usd = rub / usdRubRate
```

Недоступная цена, курс или usage создают warning, но не ломают генерацию.

## 13. Авторизация и безопасность

Используются:

- `ADMIN_LOGIN` со значением в защищённом `.env`;
- `ADMIN_PASSWORD_HASH`, но не plaintext `ADMIN_PASSWORD`;
- `ADMIN_SESSION_SECRET` не менее 32 случайных байт;
- серверные `admin_sessions`;
- cookie `cover_letter_admin`, HttpOnly, Secure, SameSite и без общего Domain;
- `SESSION_TTL_MINUTES=720`;
- `MAX_SESSIONS=5`;
- `RATE_LIMIT_PER_MINUTE=5`;
- `MAX_MESSAGE_LENGTH=140000`.

Ранее раскрытый пароль заменяется; в репозиторий попадает только описание безопасной процедуры генерации hash.

Все изменяющие браузерные запросы проходят same-origin/Origin-проверку. Административные операции требуют серверной сессии и CSRF-защиты. Nginx перезаписывает доверенные proxy-заголовки. Вход и дорогие операции защищены от перебора и чрезмерной частоты.

Технические логи содержат request ID, операцию, статус, duration, модель, usage и безопасный error code. Они не содержат ключи, cookies, пароли, системный промпт, полные тексты источников, письмо или raw LLM response.

- белые карточки на фоне `#f4f6fa`;
- текст `#172139`;
- основной синий `#245de9`, hover `#184bce`;

## 16. Production и deployment

```text
Internet → Nginx HTTPS → 127.0.0.1:8792 → Next.js
                                             ├─ Source fetcher / HH API
                                             ├─ LLM router
                                             └─ SQLite / prompt в /var/lib/cover-letter
```

Код хранится в локальном Git. Публикация в GitHub выполняется владельцем вручную. На VPS настроен read-only deploy key; deployment запускается администратором вручную по пошаговой инструкции.

Systemd:

- unit `cover-letter.service`;
- пользователь `cover-letter`, не root;
- `WorkingDirectory=/var/www/cover-letter`;
- `EnvironmentFile=/var/www/cover-letter/.env`;
- `ProtectSystem=strict`, `PrivateTmp=true`, `NoNewPrivileges=true`;
- запись только в `/var/lib/cover-letter` и `/var/cache/cover-letter`;
- код и `.env` доступны приложению только для чтения.

Nginx завершает TLS, перенаправляет HTTP на HTTPS и проксирует на loopback. Для `/api/generate` отключается buffering и задаётся достаточный timeout. Порты `8791/8792` наружу не публикуются.

## 17. Резервирование и принятые отступления

В текущей версии приложение не создаёт и не передаёт отдельные off-VPS резервные копии. Целиком VPS резервируется средствами системного администрирования. Эта внешняя процедура, её расписание и проверка восстановления не входят в код проекта.

Владельцем принят риск потери или административной перезаписи production `.env`, системного промпта и SQLite. Это не разрешает хранить их в Git или включать в deployment-архив исходного кода.

Перед миграцией deployment-инструкция должна рекомендовать убедиться в наличии актуального системного снимка VPS. Скрипты приложения не заявляют гарантию восстановления, которую они фактически не обеспечивают.
